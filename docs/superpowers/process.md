# Reader 开发流程

目标：换会话、换模型后仍能从 git 恢复背景、目标和进度，而不是依赖聊天记录。

## 1. 单一事实来源

| 内容 | 路径 |
|---|---|
| 活状态（必读） | `docs/STATUS.md` |
| 已批准规格 | `docs/superpowers/specs/` |
| 实施计划 | `docs/superpowers/plans/` |
| 本流程 | `docs/superpowers/process.md` |
| Cursor 强制规则 | `.cursor/rules/git-progress-handoff.mdc` |

聊天记录不是权威。权威是已推送的 git。

## 2. 功能增量节奏

1. 设计：用户确认后写入 `specs/`，更新 `STATUS.md`，提交并推送。
2. 计划：TDD 计划写入 `plans/`，更新 `STATUS.md`，提交并推送。
3. RED：先写或修改测试，运行并确认它因目标行为尚未实现而失败。修复缺陷时，测试必须先稳定复现缺陷。
4. GREEN：只写让当前失败测试通过的最小产品代码，运行聚焦测试确认通过。
5. REFACTOR：仅在测试保护下整理实现，再运行覆盖本次修改的测试。
6. 提交：每次代码修改验证完成后，先更新 `STATUS.md`，立即创建一个可独立回退的原子提交；提交前不得开始下一次代码修改。一个提交只服务一个目标，不夹带无关改动。
7. 推送：每次代码修改提交、每个实现任务完成及会话结束前，都推送 `origin/main`；未推送不视为已同步。
8. 收尾：测试通过、必要时重建 `Reader.exe`、按用户要求更新桌面快捷方式；`STATUS.md` 把该功能标为完成并写下一步。

## 3. 提交与推送

- 规格、计划、STATUS、规则变更与代码同等对待，必须进 git。
- 每次产品代码修改都必须对应一次提交；“修改”以一个可独立验证、可独立回退的最小行为变化为边界，而不是按保存文件或编辑器按键机械拆分。
- RED 测试可以与其对应的 GREEN 最小实现放在同一个原子提交中，但提交历史和 `STATUS.md` 必须说明先观察到 RED、再达到 GREEN；不得提交未通过且未明确标记为检查点的主线状态。
- 开始下一项修改前先确认 `git status` 中没有属于上一项但尚未提交的文件。工作区已有的无关改动不得混入提交。
- 提交说明写清「为什么」（目标），不要只列文件名。
- 禁止把进度只留在本地：实现中途若暂停，至少推送 STATUS + 当前提交。
- 推送失败（权限/账号）必须写进 STATUS 的阻塞项，不能假装已同步。

## 4. 新会话启动

1. 读 `docs/STATUS.md` 和本流程。
2. 读当前目标指向的规格与计划，确认下一项尚未完成的 TDD 任务。
3. 运行 `git status` / `git log`，识别未提交、未推送或与当前目标无关的改动。
4. 只有在目标、RED 测试和提交边界明确后才修改产品代码。

不要依赖旧聊天记录推断产品方向；若 git 中的目标或状态不完整，先补齐并提交，不得直接开始实现。
